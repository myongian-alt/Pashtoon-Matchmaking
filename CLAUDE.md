### Supabase migrations

Migrations live in `supabase/migrations/`, numbered, and must be applied **in order** — each depends on ENUMs/tables an earlier one creates. `deploy-migrations.js`, `deploy-direct.js`, and `scripts/run-migrations.js` all attempt a service-role/API push but fall back to "deploy manually" in their own error handling — don't use them.

The working path is the Supabase CLI (`supabase` is installed; run `supabase login` interactively first, then `supabase link --project-ref ngohyujweyxmrbbusufa`). **Important**: this project's migrations were originally applied by hand through the Dashboard SQL Editor, so the CLI's remote migration-history table does not necessarily reflect reality — `supabase migration list` can show every local migration as "not applied" even when the tables already exist. Before ever running `supabase db push`:
1. `supabase db query --linked "select table_name from information_schema.tables where table_schema='public';"` (and similarly check `pg_policies`/`storage.buckets` for non-table migrations) to see what's actually live.
2. `supabase migration repair --status applied --linked <versions...>` to mark the already-applied ones without re-running them.
3. `supabase db push --dry-run` to confirm only the genuinely-missing migrations would run, then `supabase db push --yes`.

Skipping this and running a blind `db push` will try to `CREATE TYPE`/`CREATE TABLE` things that already exist and fail loudly (or worse). `DEPLOY_MIGRATIONS.sql` is a pre-bundled copy of migrations 001–007 only — it's stale and excludes everything from 008 onward; ignore it in favor of the CLI flow above.

## Architecture

### Provider nesting & navigation (`src/navigation/AppNavigator.tsx`)

```
FormProvider > UserProvider > ProfileHydrationBridge > NotificationsProvider > NavigationContainer > Stack.Navigator
```

`RootStackParamList` in this file is the single source of truth for every screen and its params — keep it synchronized when adding/removing screens. Navigation flow: `Splash → Onboarding → Declaration → ChooseGender → AuthSelection → (EmailAuth | PhoneAuth→OtpVerification | guest) → Tabs`, with `ProfileCompletion`, `ProfileForm`, `PaymentSuccess`, `ProfileDetail`, `Premium`, `Chat`, `LikesYou`, `WhoViewedMe`, and `NewPassword` branching off the stack. `Declaration` (`DeclarationScreen.tsx`) is a mandatory checkbox-gated "User Declaration & Community Agreement" screen — `ChooseGender` is only ever navigated to from there (confirmed by grepping every `navigate('ChooseGender')` call site), so don't add a second entry point into `ChooseGender` without also gating it behind the same agreement, or the requirement becomes bypassable. `NewPassword` is unusual among these — it's reached imperatively (via `navigationRef`/`navigateTo` in `src/navigation/navigationRef.ts`) from a `PASSWORD_RECOVERY` auth event rather than from a normal screen's `onPress`; see "Forgot password" below. `Tabs` (`TabNavigator.tsx`) holds 6 bottom tabs: Discover, Home, Favorites, Messages, Notifications, Account. There are two separate tab-bar implementations that must be kept in sync manually — the real `Tab.Navigator` in `TabNavigator.tsx`, and `components/common/AppBottomNav.tsx`, a lookalike strip manually rendered on stack screens that live outside `Tabs` (`ProfileDetail`, `ProfileForm`, `ProfileCompletion`, `Premium`, `PaymentSuccess`) since those aren't nested inside the real tab navigator.

`LikesYou` and `WhoViewedMe` are reached from a heart-icon/badge button pair in `ProfileDiscoveryScreen`'s header (not from a tab — the tab bar was already at 6), each showing a live unread-style count. `Chat` is reached from `MessagesScreen` (the Messages tab, conversation inbox) or directly from a matched profile's card in Discover.

`AccountScreen` (the Account tab) shows a guest empty-state (sign-in prompt) when `isGuest`; otherwise it's the only place in the app that surfaces subscription status, payment history, verification status, discovery preferences (`user_preferences` table), notification/email/phone settings, account deactivation, and sign-out.

Auth success (email sign-in/up, OTP verify) resets navigation straight to `Tabs`, not `ProfileForm` — profile completion is a separate, later, user-initiated flow (`Home → ProfileCompletion → ProfileForm`).

**`SplashScreen` skips the whole onboarding chain for an already-authenticated returning session** — it waits for both its own minimum display time and `UserContext`'s `loading` to resolve, then navigates to `Tabs` directly if `isAuthenticated`, `Onboarding` otherwise (previously it navigated to `Onboarding` unconditionally, so a returning logged-in user saw the full Onboarding → Declaration → ChooseGender → AuthSelection chain on every cold start). Since `ChooseGenderScreen` is the *only* place `selectedGender` normally gets set, and every gender-filtered Discover/Matches query depends on it, skipping straight to `Tabs` required `UserContext`'s `initAuth()` to also hydrate `selectedGender` from `public.users.gender_preference` for a restored session — without that, a returning user's Discover feed would silently show both genders for the rest of the session. If you touch this flow, verify with a real reload (not just a fresh signup) that gender filtering still works immediately, not just that navigation lands on the right screen.

`ProfileFormScreen` is a two-phase flow, not a single linear wizard: a **required** phase (`MANDATORY_FIELDS` - name, DOB, phone, marital status, country, city, education, profession) that's actually validated before continuing (unlike the rest of the form, which never validates), then an **optional** phase (`optionalSections`/`optionalFieldConfigs` - Photos, Physical, Career, Financial, Religious, Values, Family, Emotional, Lifestyle, Marriage) that can be finished from any section via "Skip remaining & finish", not just the last one. Finishing (from any point in the optional phase) saves the profile and navigates to `ProfileCompletion`, which now has its own "Skip" (header button + inline link) going straight to `Tabs` → Discover instead of requiring payment. Returning users with all mandatory fields already filled skip straight to the optional phase on reopening the form (checked via `getMissingMandatoryFields(formData)` at mount).

`ProfileHydrationBridge` (defined inline in `AppNavigator.tsx`) loads a signed-in user's saved `profiles` row + `profile_photos` back into `FormContext` once per session. It has to sit inside both `UserProvider` (for `userId`) and `FormProvider` (for `updateFormData`), which is why it's a bridge component rather than logic inside either context.

`App.tsx` vs `App.web.tsx`: native wraps the navigator in `GestureHandlerRootView`; web doesn't need it and just renders the navigator directly (Metro/webpack resolve `.web.tsx` automatically for the web target). Both now also call `useFonts()` (`@expo-google-fonts/fraunces` + `@expo-google-fonts/karla`) and block on a small themed loading view until it resolves, before mounting `AppNavigator` — `theme/typography.ts` still only declares a `'System'` stack, so any screen wanting the Fraunces/Karla look has to reference the loaded family names directly (e.g. `fontFamily: 'Fraunces_600SemiBold'`) rather than through `theme.typography`; `ChooseGenderScreen`/`OnboardingScreen`/`DeclarationScreen` are the current examples. Adding a new weight/style means adding both the import in `App.tsx`/`App.web.tsx`'s `useFonts()` call *and* using the exact exported name (e.g. `Karla_600SemiBold`) — a typo'd family name silently falls back to the system font with no error.

### State

- **`UserContext`** — auth/session state (hydrated from `supabase.auth.getSession()` + `onAuthStateChange`), plus `selectedGender`, `isGuest`, `profileCompleted` (mirrored to both AsyncStorage and the `user_app_state` table). Also handles the `PASSWORD_RECOVERY` auth event (see "Forgot password" below).
- **`FormContext`** — the ~90-field matrimonial profile form (`ProfileFormData`), held entirely in memory. `calculateProfileStrength()` computes a fill-rate client-side; it is not auto-persisted anywhere — callers must pass the computed value in explicitly when saving.
- **`NotificationsContext`** — backed by the real `notifications` table (`getNotifications`/`markNotificationAsRead`/`markAllNotificationsAsRead` + a `subscribeToNotifications` realtime channel appending new rows live). Was 3 hardcoded items until this was wired up; `src/data/notifications.ts` still exists only for the `Notification` type.

### Data layer (`src/lib/`)

- **`supabase.ts`** — client + a hand-written `Database` type that only covers `users`/`profiles`/`subscriptions`/`notifications`/`messages` (not the full 15-table schema). Reads `EXPO_PUBLIC_SUPABASE_URL`/`EXPO_PUBLIC_SUPABASE_ANON_KEY` from `.env` (Expo inlines `EXPO_PUBLIC_*` into the client bundle automatically, no dotenv/babel plugin needed — built into the SDK since 49) and throws immediately if either is missing. Previously these were hardcoded string literals directly in this file; fixed during a security audit — the anon/publishable key is designed by Supabase to be public (RLS is the real boundary), so this wasn't a secret leak, but hardcoding meant rotating it required a code change and the same value was duplicated across 5+ files. The unprefixed `SUPABASE_URL`/`SUPABASE_ANON_KEY` copies still exist in `.env` for the Node-only deploy scripts, which read `process.env` directly and don't get Expo's inlining.
- **`auth.ts`** — thin wrappers over Supabase Auth (email, phone OTP, Google OAuth, session, reset, `updateEmail`/`updatePhone` — both go through `supabase.auth.updateUser()` and typically require the user to confirm the change via a link/code before it takes effect).
- **`database.ts`** — all CRUD/RPC calls: profiles, discovery, likes, connections, matches, messaging (`getConversations`/`getConversationWithUser`/`getMessages`/`sendMessage`/`markConversationAsRead`/`subscribeToMessages`), notifications, payments, verification, moderation (`submitReport`/`blockUser`/`unblockUser`/`getBlockedUsers`), profile views (`trackProfileView`/`getProfileViewers`), shortlist (`getShortlistedProfiles`/`removeLike`), discovery preferences (`getUserPreferences`/`upsertUserPreferences`), account settings (`getAccountSettings`/`setNotificationsEnabled`/`deactivateAccount`), push token storage (`savePushToken`), realtime channel subscriptions, plus the `upsertCurrentUserProfile` / `mapProfileRowToFormSnapshot` save↔hydrate pair and `syncProfilePhotos` / `getProfilePhotos`.
- **`storage.ts`** — uploads picked images to the `profile-photos` Storage bucket (fetch → arrayBuffer → upload, the standard RN/Expo pattern) and returns a public URL.
- **`aiCoach.ts`** — rule-based (not LLM) profile-completeness tips and match recommendations, scored by city/education/profession/age overlap.
- **`selfProfile.ts`** — `buildSelfProfileFromForm(formData, selectedGender)`, the one shared mapping from in-memory `FormContext` state to the object `ProfileDetailScreen`'s `isSelfProfile` view expects. Used by `HomeScreen`, `ProfileFormScreen`, and `AccountScreen` — extend this instead of re-deriving the shape a fourth time.
- **`pushNotifications.ts`** — `registerForPushNotificationsAsync(userId)`, called once per session from `ProfileHydrationBridge`. Safely no-ops on web, in Expo Go, and whenever `app.json`'s `expo.extra.eas.projectId` is unset (none of which this project has resolved yet — Expo Go dropped remote push support entirely as of SDK 53, and no `eas init` has been run). Getting real pushes delivered additionally needs a server-side sender (an Edge Function reading `public.push_tokens` and calling Expo's push API) that doesn't exist yet — this module only covers client-side token registration.
- **`authDeepLink.ts`** — native-only handler (no-ops on web) for the password-recovery deep link. Reads the incoming URL via `expo-linking`, pulls `access_token`/`refresh_token`/`type=recovery` out of it, calls `supabase.auth.setSession(...)`, and navigates to `NewPassword` directly (see "Forgot password" below for why it can't just rely on an auth event like the web path does). Initialized once from a `useEffect` in `AppNavigator`.

### Forgot password

`EmailAuthScreen` has a "Forgot password?" link → a modal that calls `resetPassword(email)` (`auth.ts`, wraps `supabase.auth.resetPasswordForEmail`). Completing the flow (after the user clicks the emailed link) is handled differently per platform, because `supabase.auth.setSession()` always fires a `SIGNED_IN` event, never `PASSWORD_RECOVERY` (checked directly against the installed `@supabase/auth-js` source):
- **Web**: `supabase.ts` sets `detectSessionInUrl: Platform.OS === 'web'` — the SDK reads the recovery tokens straight out of `window.location` at client-init time and fires a real `PASSWORD_RECOVERY` event, which `UserContext`'s auth listener catches and navigates to `NewPassword` (via `navigationRef`/`navigateTo`, see below).
- **Native**: there's no `window.location`, so `authDeepLink.ts` extracts the tokens from the incoming `Linking` URL by hand, calls `setSession()`, and navigates to `NewPassword` immediately itself rather than waiting for an event that will never come.

`NewPasswordScreen` (`src/screens/auth/`) is the actual "set a new password" form, calling the new `updatePassword()` in `auth.ts` (`supabase.auth.updateUser({ password })`).

Two gotchas hit while building this, both fixed:
1. **`navigationRef.navigate()` silently no-ops if called before `NavigationContainer`'s `onReady` fires** (e.g. a recovery link processed very early in app boot). `src/navigation/navigationRef.ts` queues the last requested navigation and `AppNavigator`'s `NavigationContainer` flushes it via `onReady={flushPendingNavigation}` — don't call `navigationRef.navigate` directly from outside a screen; go through `navigateTo()`.
2. **`SplashScreen` unconditionally called `navigation.navigate('Onboarding')` 1.4s after its mount animation, with no guard** — on a cold start via a recovery deep link, this stomped over the `PASSWORD_RECOVERY`-triggered navigation to `NewPassword` a beat later (confirmed via Playwright: the event fired and the navigate call happened, but the screenshot 4s later showed Onboarding anyway). Fixed by guarding the timeout: only navigate to Onboarding if `navigationRef.getCurrentRoute()?.name === 'Splash'` is still true when it fires. Any future "auto-advance after N seconds" logic in this app needs the same guard, or it'll clobber whatever a deep link/auth event already navigated to.

Verification note: `supabase.auth.resetPasswordForEmail` was tested against `@example.com`-style throwaway addresses used everywhere else in this project's testing and got an inconsistent `email_address_invalid` (sometimes accepted, sometimes rejected for no code-visible reason) — this looks like Supabase-side validation/rate-limiting on the `/auth/v1/recover` endpoint specifically (signup accepts the same addresses fine), not a client bug. The full "click the link → land on NewPassword → set a new password → old password stops working, new one works" path was verified end-to-end by constructing a `#access_token=...&refresh_token=...&type=recovery` URL from a real password-grant login (structurally identical to what a genuine recovery link produces) and driving it through Playwright — not by actually receiving and clicking a real email, since no real inbox is available in this environment.

### Database (`supabase/migrations/`)

36 migrations, 19+ tables, ~39 enums, RLS enabled on every table, and heavy trigger automation: auto-create `user_preferences` on signup, auto-create a `match` when a `like` becomes mutual (migration 017), auto-create a `conversation` when a `match` is inserted, auto-accept mutual `connections`, auto-notify on like/request/message/match/payment/verification, auto-sync `profile_verification.is_verified` into `profiles`. Helper RPCs: `is_user_premium`, `process_payment` (now `SECURITY DEFINER`, see below), `get_unread_notification_count`, `get_user_report_count`.

**`supabase_realtime` publication had zero tables in it until migration 033** — `subscribeToMessages`/`subscribeToNotifications` (`database.ts`) had been calling `.channel(...).on('postgres_changes', ...)` since migrations 004/005, but `postgres_changes` has nothing to broadcast unless the table is in that publication, so both were silently inert (UI only ever updated via manual refetch, never a live push) until this was caught and fixed. If you add a new realtime subscription, check `SELECT * FROM pg_publication_tables WHERE pubname = 'supabase_realtime'` first — don't assume a table is included by default.

**Edge Functions** (`supabase/functions/`) — deployed via `supabase functions deploy <name>` (no Docker required despite the CLI's warning), secrets set via `supabase secrets set KEY=value` (never as `EXPO_PUBLIC_*` — those get inlined into the client bundle). `SUPABASE_URL`/`SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY` are auto-injected into every deployed function's environment; only feature-specific secrets need setting explicitly. `request-contact-details` is the first one: records a row in `contact_requests` and emails the admin via Resend (`RESEND_API_KEY`/`ADMIN_EMAIL` secrets) when a user taps "Request Contact Details" on `ProfileDetailScreen` — replaces the old $30 payment paywall on that button, for now. Resend's free/unverified tier only delivers to the email the Resend account itself signed up with; sending to arbitrary admin addresses needs a verified domain.

Migrations are applied via `supabase db query --linked -f <file>` + `supabase migration repair --status applied <version>`, **not** `supabase db push`. `db push` (even `--dry-run`) requires an interactive Postgres DB password prompt and hangs forever non-interactively in this environment (`--password`/`SUPABASE_DB_PASSWORD` isn't set anywhere) — `db query --linked` and `migration repair` go through the Management API instead and don't need it. `supabase migration list` still works fine for checking sync state.

**Three RLS/grants gotchas found via live REST testing (not caught by RLS review alone — verify with real HTTP calls, not just reading policy SQL) that will bite again if repeated:**
1. **Supabase auto-grants full table-level `arwdDxtm` (ALL) to `anon`/`authenticated` on every new table**, via a project-level `ALTER DEFAULT PRIVILEGES` on the `public` schema (`SELECT * FROM pg_default_acl` shows it) — this happens regardless of what a migration's own `GRANT` statements say. **A column-level `GRANT INSERT/UPDATE (col1, col2)` is not a security boundary by itself** — the broader table-level grant from the default ACL still lets any authenticated user write every column unless the table-level privilege is explicitly `REVOKE`d first (see migration 024, which had to revoke table-level INSERT/UPDATE on `profile_verification` before the column-level grants from migration 019 actually restricted anything — until then, any signed-in user could set `is_verified = TRUE` on their own row directly).
2. **`INSERT ... ON CONFLICT DO UPDATE` (i.e. `.upsert()`) requires table-level UPDATE privilege**, even when every column in the `SET` list has its own column-level grant and a plain `UPDATE` on those same columns works fine. If a table intentionally only grants column-level write access (like `profile_verification`), never use `.upsert()` against it from the client — do a plain `.update().eq(...)`, and only `.insert()` as a fallback when the update matched zero rows (see `requestProfileVerification` in `database.ts`).
3. **Postgres applies a table's SELECT policy to the row returned by `INSERT ... RETURNING`, not just the INSERT policy's `WITH CHECK`** — and PostgREST's default `Prefer` (when the client doesn't override it, which `supabase-js` doesn't unless you chain `.select()`/pass `returning: 'minimal'`) is `return=representation`, i.e. every insert is effectively `RETURNING *`. If a table's SELECT policy is asymmetric (e.g. `profile_views`: only the *viewed* user could originally read a row, not the *viewer* who created it), **every insert by the writer fails with a misleading `42501 new row violates row-level security policy` error**, indistinguishable from a real INSERT-check failure. This silently broke `trackProfileView()` end-to-end until migration 026 widened the SELECT policy to also allow `viewer_id = auth.uid()`. When adding a write-heavy table with an asymmetric SELECT policy, either make sure the writer's own row satisfies SELECT too, or have the client explicitly request minimal return for that call.

Also: `process_payment()` (migration 025) is deliberately `SECURITY DEFINER` with `SET search_path = public, pg_temp` and its own internal `auth.uid() != user_id_param` check — this was necessary because the payments/subscriptions RLS design (row-owner `WITH CHECK`) would otherwise let a user directly `POST /rest/v1/payments` a self-authored "completed" row bypassing the RPC entirely (free premium). Follow this pattern (SECURITY DEFINER + explicit internal auth check, table-level INSERT/UPDATE revoked from `authenticated` for that table) for any future money- or trust-affecting write path — don't rely on row-owner RLS alone when the row's *content* (not just its owner) has to be trustworthy.

**`WITH CHECK (true)` is a recurring mistake pattern in this codebase's earlier migrations, not a one-off** — a full security audit (migrations 029-032) found FOUR tables (`matches`, `notifications`, `reports`, `ai_user_nudges`) with a write policy of `WITH CHECK (true)`, each written assuming "only my trigger will ever insert here" without accounting for Supabase's default table-grants making that assumption false for direct client calls too (same root cause as the `profile_verification` column-grant issue above). Three were live-exploited during the audit with a single authenticated REST call each: forging a `matches` row auto-created a real conversation with a non-consenting user *and* bypassed the premium messaging paywall; forging a `notifications` row let one user inject arbitrary phishing content into any other user's feed; forging a `reports` row let one user impersonate another as the filer. Fixed by marking every writer trigger function `SECURITY DEFINER` (pinned `search_path`) and revoking the direct-client grant — the same `process_payment()` pattern, applied three more times. **When adding any new `_system_insert`/`_admin_write`-style policy meant for "only a trigger writes here," always pair it with `SECURITY DEFINER` on that trigger + `REVOKE` on the table in the same migration — never ship the permissive policy first and mean to lock it down later.**

Other load-bearing things to know before changing this layer:
- **`public.profiles` has no `education` column — it's `education_level`, a strict Postgres enum (`education_level_enum`: `high_school`/`bachelors`/`masters`/`phd`/`diploma`), separate from `degree_name` (free-text VARCHAR).** This was previously a serious live bug — `upsertCurrentUserProfile`, `getDiscoveryProfiles`, `getMatches`, and two functions in `aiCoach.ts` all referenced the nonexistent `education` column and failed with Postgres `42703` on every real (non-guest) use, confirmed by driving a real signup through the app. **Fixed**: all five now use `education_level`/`degree_name` correctly, via the `EDUCATION_LEVEL_MAP`/`EDUCATION_LEVEL_DISPLAY` pair in `database.ts` (same pattern as `MARITAL_STATUS_MAP`/`MARITAL_STATUS_DISPLAY` — UI dropdown strings like `'Bachelors'` never match Postgres enum values like `bachelors` directly, so any enum-backed field needs both a write-direction and read-direction map). If you add another enum-backed profile field, follow this same two-map pattern rather than passing the UI string straight through.
- **`create_user_preferences_on_signup` (the trigger that fires on every first insert into `public.users`) had its own separate enum-cast bug**, unrelated to the one above: its `CASE WHEN ... THEN 'female' ELSE 'male' END` resolved to `text`, which Postgres won't implicitly cast to `gender_seeking_enum` inside an INSERT built from a CASE expression. This silently broke `ensureCurrentUserRecord` (called by `upsertCurrentUserProfile` before every profile save) for any user whose `public.users` row didn't already exist — i.e. every real first-time profile save. **Fixed in migration 014** by casting the CASE expression explicitly (`(...)::gender_seeking_enum`). Both this and the `education` bug had to be fixed together before profile saving actually worked end-to-end (verified by completing the real `ProfileForm` flow and confirming the row landed correctly in `profiles`).
- **`.single()` vs `.maybeSingle()`**: several read functions in `database.ts` originally used `.single()` on tables where a zero-row result is the common case (no subscription yet, no profile yet, etc.) — `.single()` throws `PGRST116` in that case instead of returning `null`. `getProfile`, `getSubscriptionStatus`, and `getProfileVerificationStatus` have been fixed to `.maybeSingle()`; if you add a new one-row-per-user lookup, default to `.maybeSingle()` unless the row is truly guaranteed to exist (e.g. `user_preferences`, which has an auto-create trigger).
- **`upsertCurrentUserProfile` only persists a subset of the form's ~90 fields** (name, DOB, marital status, city, nationality, phone, education level, degree name, profession, about-me, profile strength). The rest — Physical, Financial, Religious, Values, Family, Emotional, Lifestyle, Marriage sections — are filled in the UI but currently dropped on save. Known gap, not something to silently "fix" by expanding scope without checking first.
- **`marital_status_enum` includes `married`** (migration 013, deployed) alongside `never_married`/`divorced`/`widowed`/`separated`, for users who are currently married (e.g. considering a second marriage). Postgres enum values can only be appended, not inserted mid-list transactionally with their first use — a new enum value migration should only ever add the value, never write/read it in the same migration.
- **`profiles`/`profile_photos` SELECT policies gate on `is_verified` OR an active `users` row** (migration 010, deployed). **Photo upload** needs the `profile-photos` Storage bucket + owner-write RLS + the gallery `display_order` cap raised from 4 to 5 (migration 011, deployed).
- **Real profiles were invisible in Discover for anyone but their own owner from migration 016 until migration 027.** The "active users row" half of the migration 010 policies above did `EXISTS (SELECT 1 FROM users u WHERE u.id = <target>.user_id AND u.is_active = true)` against the raw `public.users` table. Migration 016 (fixing a PII leak) tightened `users`' own RLS to `auth.uid() = id` only — and that also governs this EXISTS subquery, since Postgres enforces a table's RLS on every reference to it, including from inside another table's policy. The subquery could therefore only ever see the caller's *own* row, so it silently evaluated to `false` for every other user's profile — real signups have been undiscoverable (falling back invisibly to the client-side sample profiles, which is why nobody noticed) since the PII fix shipped. **Fixed in migration 027** by pointing both policies at `public.users_public` instead (a plain view, which runs with the view owner's privileges rather than the querying role's — confirmed empirically, not just assumed). If a future RLS policy needs to check something about a *different* user, referencing the raw `users` table will hit this same trap; go through `users_public` (or a `SECURITY DEFINER` helper) instead, and verify empirically (query as a real second user) rather than trusting the policy SQL by itself — this one read as correct and wasn't.
- **The `id` on list/nav items is not always the target's `user_id`.** `ProfileListItem` and the `ProfileDetail` nav param carry a separate `userId` field for this reason — `id` can be a `profiles.id` (discover) or a `matches.id` (matches tab). Anything writing to `likes`/`connections` (which reference `users.id`) must use `.userId`, not `.id`.

### Known environment gotchas

- Phone OTP needs a Phone provider + SMS provider configured in Supabase Auth — `"Unsupported phone provider"` is a backend config issue, not a client bug. Supabase's Test Phone Numbers/OTPs must be entered **without** a `+` prefix (e.g. `971555826960=123456`). Real delivery failures are usually Twilio routing/config (`21704` no sender in service, `21612` invalid destination-route pairing) — a 200 from `/auth/v1/otp` does not mean the SMS was delivered.
- Running the web dev server with `CI=1` disables Metro's file-watcher/reload — fine for a one-off headless check, but edits won't hot-reload; drop `CI` (or restart the server) for iterative work.
- Never hardcode service-role keys — the deploy scripts read `SUPABASE_SERVICE_ROLE_KEY` from the environment; don't commit it or paste it into scripts/docs.
- `expo-status-bar` was previously a dependency with no code anywhere importing it (dead weight from the initial template) — removed. If status bar styling is ever actually needed, re-add it and import it in `App.tsx`/`App.web.tsx` at that point, don't just have it sitting in `package.json` unused. (It had also been pinned to an exact `56.0.0` version with bad peer-dependency metadata at one point, which broke plain `npm install` with `ERESOLVE` — moot now that it's gone, but if it's re-added, don't pin an exact version — use `~56.0.x` or later.)
- **Payments are simulated, not real Stripe.** `processPayment()`/`process_payment()` record a `payments`+`subscriptions` row and grant access immediately — no card is ever actually charged, and `'card'` as a `payment_method` doesn't mean a card was collected. Real billing needs: a Stripe account + secret key held server-side only (an Edge Function, never the client), `@stripe/stripe-react-native` (which needs an EAS dev/production build — it can't run in Expo Go), and a webhook Edge Function that verifies Stripe's signature before calling `process_payment()` with the real charge ID as `transaction_id_param`. None of that exists yet.
- **`Alert.alert(...)` is silently a no-op on the web build — including single-button informational calls, not just multi-button confirms.** Confirmed via Playwright with a `page.on('dialog', ...)` listener attached: no browser dialog ever fires and no button's `onPress` ever runs, for any button count. This was first fixed for `handleBlock` (a real `<Modal>` with Cancel/Block) and the report modal. It was found *again* on `ProfileDetailScreen` for `handleSendMessage`/`handleRequestContactDetails`/`handleSendInterest`'s error paths (e.g. tapping "Request Contact Details" on a sample/demo profile — one without a real `userId` — called `Alert.alert('Not available', ...)` and produced literally zero visible feedback, which read as a broken button, not a bug in the underlying feature). **Fixed properly this time**: `ProfileDetailScreen.tsx` no longer imports `Alert` at all — every call site was replaced with a `showBanner('success' | 'error', message)` helper (state + a colored banner rendered under the header, auto-dismissing after ~3.5s), which is visible on both web and native. If you add a new screen that needs to surface a transient success/error message, copy this banner pattern rather than reaching for `Alert.alert` — it will look like it works in code review and then silently do nothing the moment a real user hits that path on web.
- **The premium/subscription paywall on messaging has been removed, for now** — `ProfileDetailScreen`'s "Send a Message" no longer checks `isUserPremium` (that function still exists in `database.ts`, just unused); any signed-in user can message any profile directly via `getOrCreateConversation`, not just mutual matches. The "View Contact Details" button was also changed from navigating to the `$30` `ProfileCompletionScreen` payment flow to instead calling the `request-contact-details` Edge Function (see above) — no payment screen appears in that path anymore. `ProfileCompletionScreen`/`PremiumScreen` and their payment UI still exist and are still reachable from `HomeScreen`/`ProfileFormScreen`'s own-profile-completion nudges (unrelated, untouched) — only the two `ProfileDetailScreen` entry points were rewired.
- **Supabase Auth returns `''` (empty string), not `null`, for the phone/email field a user didn't sign up with** — an email/password user has `user.phone === ''`. `ensureCurrentUserRecord()` (`database.ts`, called by `upsertCurrentUserProfile` before every profile save) was upserting that `''` as-is into `public.users.phone`/`.email`, both `UNIQUE` columns. The **first** email-only signup to ever save a profile claimed `''` for `phone`; **every email-only user after that got a duplicate-key error and their own profile save silently failed** — confirmed live (a real production account already had `phone: ''` from normal usage, and the second test account hit the collision immediately). Fixed by using `user.phone || null` / `user.email || null` (not `??`, which only catches `null`/`undefined`) plus a data migration (035) to null out the row that had already been corrupted. If you ever write a Supabase Auth `user.*` field into a `UNIQUE` column, normalize empty string to `null` first.
- **Default Supabase ACLs grant `anon` (not just `authenticated`) full CRUD on every new table, and this had never been revoked for `messages`/`notifications`/`matches`** (only `authenticated` was tightened, in migrations 029/030). Not an active exploit — every policy on those tables keys off `auth.uid()`, which is `NULL` for `anon`, so RLS already denied it in practice — but confirmed and closed anyway in migration 036 (`REVOKE ... FROM anon`) as defense-in-depth, verified live (anon now gets a hard `42501 permission denied` instead of relying solely on RLS filtering to an empty result). When creating a new table, revoke unneeded grants from **both** `anon` and `authenticated` explicitly rather than assuming RLS alone is sufficient — check `information_schema.role_table_grants` for both roles, not just one.
